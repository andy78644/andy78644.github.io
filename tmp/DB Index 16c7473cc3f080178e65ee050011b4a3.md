# DB Index

Owner: Eric Lin

## **簡介**

---

索引是特殊的資料結構，儲存集合中部分資料的排序結構，讓 MongoDB 可以快速定位文件，避免全集合掃描（Collection Scan）。

## 優點

1. 提升查詢效能
    - 透過索引可以不用掃描全部文檔，提升查詢執行效率
2. 支援排序操作
    - 所以可以支援排序查詢，減少在記憶體進行排序

## 缺點

1. 會導致寫入的成本變高，需要去更新索引的資料
2. 佔用額外硬碟空間

## index 機制

---

- B-tree (多子樹的tree)的架構來儲存，每個節點會是 `索引鍵 + 指向文檔的指標`
- 透過 index 在 tree 上進行分類及排序
- 每次更新會重新更新有使用到該欄位的 index
- 會在多個 index 中選擇適當的 index 進行查詢
- 可以進行雙向的掃描(1 or -1)

## index 分類

---

### 單欄位索引 (Single Field Index)

- 最基本的索引類型，針對單一欄位建立。

### 複合索引 (Compound Index)

- 複合索引從集合中每個文檔的多個欄位值收集和排序資料。
    - 可以使用複合索引查詢第一個欄位或索引的任何前綴欄位。
        - index {a:1, b: 1, c: 1}  在 query {a, b} 的時候也能用到這個 index 就不需要建立另外的 index {a: 1, b: 1 }
- B-tree 會按照 index 的順序來排序
    - 複合索引是**多層排序**的結構，按照索引欄位的順序進行排序。
    - ex
        
        ```tsx
        index {a: 1, b: 1}
        // data → 會優先排 a 的資料，然後再排 b 的資料
        [
        	{0, 0} 
        	{0, 1}
        	{1, 0}
        	{1, 4}
        	{4, 3}
        ]
        ```
        
- ESR 規則，依照 ESR 的順序排序 index
    - 相等查詢（Equality）
    - 排序（Sort）
    - 範圍查詢（Range）
        - 經過 sort 之後可以直接遍歷全部的資料就不用在 memory 再進行一次 sort
        - ex
            
            ```tsx
            // data
            [
              {a: 0, b: 0, name: "user1"},
              {a: 0, b: 1, name: "user2"},
              {a: 1, b: 0, name: "user3"},
              {a: 1, b: 4, name: "user4"},
              {a: 2, b: 3, name: "user5"},
              {a: 2, b: 5, name: "user6"},
            ]
            
            // a 是 range, b 是 sort
            db.users.find({a: {$gte: 0, $lte: 1}}).sort({b: 1})
            // 在 range 時先過濾掉 a = 2 的部分
            // 此時資料的 b 會沒有經過 sort，因此取出後還要經過 memory sort
            [
              {a: 0, b: 0, name: "user1"},
              {a: 0, b: 1, name: "user2"},
              {a: 1, b: 0, name: "user3"},
              {a: 1, b: 4, name: "user4"},
            ]
            
            // a 是 sort, b 是 range
            db.users.find({b: {$gte: 2, $lte: 5}}).sort({a: 1})
            // 由於 a sort 的順序已經好了，所以只要遍歷 index 內所有的 b 並且按照原本的順序就能保持 sort a 
            ```
            
- 用於多個欄位的查詢以及排序
- 補充sort 和 range 的例子

### Partial index

- 只對符合指定過濾條件的文檔建立索引
- 可以將不需要的資料排除在 index 外
- ex
    
    ```tsx
    // 賽狗能使用的狗為還沒被出售的狗，已經出售的狗就不需要被列出 index 
    db.orders.createIndex(
      { partialFilterExpression: { status: "canBeSold" } }
    )
    ```
    

### TTL index

- 讓文檔在指定時間後**自動過期並被刪除**
- 移除過期文檔的背景任務每 60 秒執行一次，因此文檔可能在過期時間和背景任務運行之間的時間段內仍保留在集合中
- ex
    
    ```tsx
    await PT.runtimeCollection("CanEnterRequestedChIdLog").ensureIndex(
        { removeAt: 1 },
        { expireAfterSeconds: 0 },
    );
    ```
    

## 建立index時需要考慮的因素

---

1. **避免建立太多index**
    - 插入、更新和刪除操作變慢：每次資料的變更都需要更新相應的索引
        - 透過 partial index 可以避免空間的增加
    - 查詢性能降低
    - 硬碟空間增加
        - 透過 partial index 可以避免空間的增加
    - 佔用過多記憶體資源
2. 選擇欄位
    1. **避免選擇需要經常更新的欄位**
        - 更新索引欄位的值時，資料庫同樣需要更新索引，這會使更新操作變得較慢
    2. **選擇唯一性索引**
        - 新增的index的值是唯一的，資料庫可以更快定位到特定的紀錄，從而提高查詢效能
    3. **選擇經常需要排序、分組的欄位**
        - index可以顯著加快 ORDER BY 和 GROUP BY 操作
    4. 針對常用查詢建立索引
3. 需要考量欄位可能搜尋的次數以及資料量的大小
    1. 如果搜尋次數或資料量太少，建立 index 可能會造成寫入的成本高於搜尋加快的好處
4. Compound Index
    1. 遵循 ESR 原則
    2. 高選擇性的優先放在前面
        - 能把越多東西篩掉的放越前面
    3. 避免過度索引
        - 會影響寫入速度
    4. 完整的前綴匹配
        - 跳過欄位會導致需要在 memory 查詢會變成比較低效
        - index {a: 1, b: 1, c: 1, d:1 }
            - query { a, b, d}
                - 跳過 c 的話就要把 d 的所有資料全部抓出來查詢，導致效能降低
            - query {a, b, c, d}
                - 只要檢查 query 的 c 下面的 d
        - 利用 index 資料在 memory 裡面排序可能會比較快
            - index {a: 1, b: 1, c: 1, d:1 } vs index {a: 1, b: 1 }
            - 如果欄位很多的時候，query{a, b, d}
                - 如果是用第一種 index 可以直接從索引內取得數據，雖然沒有經過完整的前綴但有在索引內 (只讀索引)
                - 如果用第二種需要把所有資料庫內整個 document 抓出來找比較浪費 (索引+讀表)
